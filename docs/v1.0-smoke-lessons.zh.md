# v1.0 Smoke Test 課題總整理

> 中文版。English original: [`v1.0-smoke-lessons.md`](v1.0-smoke-lessons.md)

`migrate-to-fastapi-service` change 在 Proxmox docker + k3s Helm 上做 smoke test 期間(2026-08-09 到 2026-08-10)遇到的所有問題,集中在此。未來做類似規模的遷移時,可當作「即使 unit test 全過,deploy 時還是會爆的東西」的檢查表。

## Smoke 覆蓋範圍

| 環境 | 驗證項目 |
|---|---|
| Docker Compose on Proxmox VM | 端到端 mail flow、SSH tunnel + loopback URI 的 headless OAuth、in-replica single-flight(10 併發 `/poll`)、host cron @ 60s |
| k3s cluster(3 nodes、Longhorn) | 上述全部 + **跨 node** advisory-lock single-flight(pods on `k3s-node-1` + `k3s-node-3`、k8s Service round-robin、`1×200 + 9×409`)、跨 replica 的 Postgres-backed OAuth FlowStore、PVC token 持久化 |

期間 unit test 全程綠燈(559 → 568,加了 regression pin)。下面每個 issue 都是 pytest 抓不到、非得跑真部署才會冒出來的。

## 依類別分類

格式:**症狀 → 根因 → 修法(commit)→ 加入的預防**。

### Environment / packaging

**1. `GmailSettings` 讀 `GMAIL_*` 但 deploy templates 設 `GOOGLE_*`**
- **症狀**:container 啟動時 lifespan crash,`FileNotFoundError: OAuth client secrets not found at credentials.json` —— 我們設的 env var 根本沒被讀,settings fallback 到預設 `credentials.json` 找不到檔案。
- **根因**:`GmailSettings.env_prefix = "GMAIL_"`(v0.6.x 沿用),但我 Dockerfile ENV / `.env.example` / Helm values.yaml 全用 `GOOGLE_CREDENTIALS_PATH` / `GOOGLE_TOKEN_PATH`。openspec design D7 也用 `GOOGLE_*` —— 整條 spec-to-code 鏈都寫錯 prefix,但 code 端是 pinned 的。
- **修法**:[`de55a2d`](../commit/de55a2d) —— 全 deploy templates + Dockerfile ENV + Helm values + MIGRATION doc 從 `GOOGLE_*` 改回 `GMAIL_*`。Openspec 產物保留歷史不一致(反映當初的錯誤設計)。
- **預防**:env parity script(`scripts/check_env_parity.py`)守 compose ↔ Helm 之間的漂移,但**不會**跨檢 code 端。未來改進可 parse `BaseSettings` 子類的 `env_prefix + field_name`,驗證是否出現在 deploy templates。目前沒實作,推遲。

**2. Host bind-mount 擁有權對不上 uid**
- **症狀**:container 啟動 crash,`PermissionError: [Errno 13] Permission denied: '/data/token.json'`,`chmod 600` 明明有設。
- **根因**:container 內 uid 10001,但 host 目錄 owner 是 uid 1000(host 預設 user)。mode 600 = owner-only,container 讀不到。
- **修法**:[`755aafe`](../commit/755aafe) —— MIGRATION-v1 + deploy/compose/README.md 明確加 `sudo chown -R 10001:10001 secrets data` 步驟。
- **預防**:純 docs,沒自動化。Container 可以自癒(entrypoint 先 root 執行 chown 再 drop 到 non-root),但這樣要犧牲「pod 從一開始就 non-root」的保證,不划算。選 docs 路線。

**3. Alembic migrations 沒進 image**
- **症狀**:fresh Postgres → 第一次 `POST /poll` 500,`sqlalchemy.exc.ProgrammingError: relation "gmail_sync_state" does not exist`。
- **根因**:`.dockerignore` 排除了 `alembic.ini`(還有一個根本不存在的 `migrations/` 目錄,實際 alembic 位置是 `alembic/`,沒排除)。Dockerfile 也沒 COPY 這兩者、也沒 entrypoint 跑 `alembic upgrade head`。
- **修法**:[`10f6327`](../commit/10f6327) —— `.dockerignore` 不再排除 alembic;Dockerfile COPY `alembic.ini` + `alembic/`;新 `docker-entrypoint.sh` 在 uvicorn 之前跑 `alembic upgrade head`。Alembic 的 `alembic_version` row lock 讓多 replica 同時啟動時併發安全。
- **預防**:沒 unit test;「entrypoint 有跑 migrations」是 deploy-shape 特定的驗證。未來可加 build-time smoke:`docker run --rm image alembic current` 打拋棄式 Postgres。

### OAuth

**4. Flow store round-trip 弄丟 PKCE code_verifier**
- **症狀**:Google 同意畫面完成後,`/auth/callback` 回 400 `fetch_token_failed: (invalid_grant) Missing code verifier`。
- **根因**:`google_auth_oauthlib.flow.Flow.authorization_url()` 會自動產 PKCE 用的 `code_verifier` 存在 Flow instance 上。`oauth_flows` store 序列化時把它丟了(只留 `scopes` + `redirect_uri`),callback 時重建的 Flow 有全新的 verifier,對不上 Google 從 `/auth/start` 看到的 challenge。
- **修法**:[`cfab222`](../commit/cfab222) —— `OAuthFlowStore._serialize` 存 `flow.code_verifier`;`_reconstruct` 還原。regression test 在 `tests/coordination/test_oauth_flow_store.py::test_roundtrip_preserves_pkce_code_verifier`。
- **預防**:regression test 守未來 google-auth-oauthlib 若改欄位名。

**5. Google 回傳 scope superset 被 oauthlib 拒絕**
- **症狀**:`/auth/callback` 回 400 `fetch_token_failed: Scope has changed from "gmail.readonly" to "gmail.readonly drive drive.photos.readonly drive.appdata"`。
- **根因**:Google token endpoint 會把該 user / client 曾授權過的**所有 scope 都回傳** —— 通常是這次請求的 superset(例如你之前用同一個 OAuth client 授權過 Drive)。oauthlib 預設嚴格 equality check。
- **修法**:[`7fcb953`](../commit/7fcb953) —— Dockerfile ENV 設 `OAUTHLIB_RELAX_TOKEN_SCOPE=1` + `core/services.py` 開頭 `os.environ.setdefault(...)`(在 oauthlib import 之前)。`docs/oauth-redirect-uri.md` troubleshooting 段有寫。
- **預防**:env var 在 container 啟動與 Python process init 都無條件設置,很難意外破壞。

**6. Google OAuth client type UI 顯示不同**
- **對我們不是 bug**,但操作者體驗混亂。`Desktop app` 型 client 在 Google Cloud Console 上**不會顯示** "Authorized redirect URIs" 欄位 —— Google 自動允許 `http://localhost:*` 和 `http://127.0.0.1:*`。照 migration guide 找「加 redirect URI」步驟的操作者會找不到那個欄位。
- **修法**:[`docs/oauth-redirect-uri.md`](oauth-redirect-uri.md) 開頭明確區分 Desktop vs Web client type。

### Cron / scheduler

**7. Host crontab 的 `%` 是 end-of-command 標記**
- **症狀**:cron log 空的,`syslog` 顯示 CRON 有 firing。syslog 的 CMD 行被截斷:`(david) CMD (curl -fsS -m 55 -w ')`。
- **根因**:host cron 把 `%` 當作 end-of-command / stdin separator。未逃逸的 `%{http_code}` 讓整個 command 在 `%` 處被切斷。
- **修法**:[`9ba2b32`](../commit/9ba2b32) —— crontab.example 改用 `\%{http_code}\n` 並在檔案開頭寫這個坑。

**8. Cron **不繼承** shell env**
- **症狀**:`%` 修好後 curl 回 401。手動 shell 執行同樣指令是好的。
- **根因**:crontab 內的 `${HTTP_API_KEY}` 在 cron 執行環境下是空的 —— cron 不 source 你的 shell profile。
- **修法**:crontab.example 明白寫「把 key 值直接貼進 crontab 那行」。crontab 檔案 mode 600 → 明文寫 key 在 homelab 可接受。
- **也**:24h 後我忘記把 placeholder 換成真值 → 又 401,眼睛跳一下就懂 —— 但這是 paste-and-run 的陷阱,現在 runbook 顯眼位置有警語。

### Storage / k8s

**9. `git rev-parse --short` 跟 `$CI_COMMIT_SHORT_SHA` 長度不同**
- **症狀**:`ImagePullBackOff` + `manifest not found` —— image tag `7f155f5c` registry 找不到。
- **根因**:`git rev-parse --short` 取「能唯一識別 commit 的最短 prefix」(通常 7 char,有時更長)。GitLab CI 的 `$CI_COMMIT_SHORT_SHA` **固定 8 char**。我猜的第 8 個 char(`c`)是錯的,實際 tag 是 `7f155f51`。
- **修法**:runbook 改成「看 GitLab Container Registry UI 的實際 tag」,不要在 laptop 端算。
- **預防**:CI 驅動的部署,helm values override 應該在 pipeline 內用 `$CI_COMMIT_SHORT_SHA` 產,不是操作者手算。

**10. Helm chart 的 OAuth token 從沒被 mount 進去**
- **症狀**:pod lifespan crash,`webbrowser.Error: could not locate runnable browser` —— `get_credentials()` fallback 到 `InstalledAppFlow.run_local_server()`,headless container 內沒瀏覽器。
- **根因**:`oauth.tokenJson` 有進 k8s Secret(`secret.yaml`),但 Deployment 的 `secret` volume 只 mount `credentials.json`(`items` entry 那邊)。token.json 存在 Secret 裡但 pod filesystem 上沒有。
- **修法**:[`8c497a1`](../commit/8c497a1) —— 新 `oauth-seed` volume(mount 整個 Secret 內容)只掛給新的 init container `seed-token`,由它在首次啟動時把 `token.json` 複製到 `/data/`。guard `[ ! -f /data/token.json ]` 避免覆蓋 in-cluster `/reauth` 寫入的 token。若 `oauth.tokenJson` 為空(fresh deploy),init container no-op 並印友善訊息。
- **預防**:`helm template` render 已被 `tests/deploy/test_helm_chart.py` 覆蓋,但只 assert kind 存在,沒驗證 volume mount 正確性。未來可加 test 去 parse render 的 Deployment,assert 每個預期的 volume 都有 mount 到位。

**11. RWO PVC 阻擋 multi-replica**
- **症狀**:`helm upgrade --set replicaCount=2` → 第二個 pod 排到不同 node,卡在 ContainerCreating,`Multi-Attach error for volume ... Volume is already used by pod(s) ...`。
- **根因**:預設 `persistence.accessMode: ReadWriteOnce` 讓 PVC 一次只能掛一個 node。第一個 pod 在 node-3,第二個 pod 排到 node-1 → attach 失敗。
- **修法**:[`77923b7`](../commit/77923b7) —— values.yaml 顯眼位置寫 RWO ↔ `replicaCount` 的相容契約。chart 預設保留 RWO(通用相容);要 multi-replica 的 user 必須改 RWX 且 storage class 要支援。
- **預防**:純 docs。理論上 chart 可寫一個 template 在 `replicaCount > 1 && accessMode == "ReadWriteOnce"` 時 render 一個警告 comment,但 Helm 沒有 first-class validation warning,要用 `.Files.Get` + `fail` 反而 user-hostile。

**12. Longhorn RWX 要求每個 node 裝 nfs-common**
- **症狀**:`persistence.accessMode: ReadWriteMany` 的 `helm upgrade` → `FailedMount: mount failed ... bad option; for several filesystems (e.g. nfs, cifs) you might need a /sbin/mount.<type> helper program`。
- **根因**:Longhorn 用 NFS(share-manager)實作 RWX。NFS mount 要求 `nfs-common`(Debian/Ubuntu)或 `nfs-utils`(RHEL/CentOS)裝在每個會跑 RWX pod 的 node 上。
- **修法**:沒 code 改動(Longhorn 前置需求,不是 chart 的問題)。runbook Phase A 加了 `for node in ...; do ssh $node 'sudo apt install -y nfs-common'; done`。
- **預防**:純 docs。這是 Longhorn side 的前置條件,任何要用 RWX 的 workload 都要。

**13. Pod 消失時 port-forward 一起死**
- **症狀**:10 併發測試回 10 × `000`(empty reply),而不是預期的 `1×200 + 9×409`。kubectl 印 `sandbox not found`。
- **根因**:`kubectl port-forward svc/...` 綁定特定 pod。任何 pod restart / helm upgrade 換 pod → forward 失效。
- **修法**:重試 —— 重開 port-forward,重跑測試。生產用 ingress / LoadBalancer(沒這問題)。
- **預防**:runbook 現在寫「port-forward 中途出錯就重啟;ingress 是生產路徑」。

### Database

**14. `CREATE DATABASE` 沒明確指定 encoding 可能 fallback 到非 UTF-8**
- **症狀**:analyze + notify 都跑完,`_persist` crash,`psycopg.errors.UntranslatableCharacter: unsupported Unicode escape sequence`,寫中文 keywords 失敗。
- **根因**:Postgres 從 `template1` 繼承 encoding。某些系統 `template1` 是 `SQL_ASCII` —— psycopg 用 server-side encode 寫中文 JSON 會炸。v0.6.x 使用者的 production DB 剛好是 UTF-8;smoke DB 建立時沒指定 `WITH ENCODING 'UTF8'`,繼承了 SQL_ASCII。
- **修法**:沒 code 改動 —— 操作者側 DB provisioning。重建 DB 用 `CREATE DATABASE ... WITH ENCODING 'UTF8' TEMPLATE template0 LC_COLLATE 'C' LC_CTYPE 'C';`。
- **預防**:MIGRATION-v1 troubleshooting appendix 有寫。未來改進可讓 `build_services` 開機時 `SHOW server_encoding`,不是 UTF8 就拒絕啟動。

## Smoke 實際驗證到的東西(正面成果)

- **D3 advisory lock cross-replica** —— 用 2 個 pod 在 2 個不同 k3s node 上、10 併發 `POST /poll` → 精確 1×200 + 9×409 驗證。不是 same-loop asyncio test;是真正的跨網路、跨 node 協調測試。
- **D8 headless OAuth flow** —— 全 round-trip 走 SSH tunnel + loopback URI(Desktop OAuth client 的特例) + PKCE + token reload。
- **D17 multi-replica readiness** —— Postgres-backed OAuth FlowStore 讓 `/auth/callback` 可以命中任何 replica;2 pod 積極透過 `oauth_flows` table + Longhorn RWX PVC 共享狀態,驗證通過。
- **Alembic 自動 provisioning** —— fresh DB → entrypoint 跑 migrations → pod 起 uvicorn → `/healthz` 綠。
- **Init-container token seeding** —— 空 PVC + 有內容的 Secret → main container 起來前 token 已 seed 到 `/data/token.json`。

## 未來類似規模遷移的操作者 checklist

大致順序:

1. Unit test suite 全綠。
2. `openspec validate` 全綠。
3. `docker build` + `docker run` 打拋棄式 Postgres 的 smoke。
4. Container 起來、`/healthz` 回 200 且所有 check 為 true。
5. 端到端使用者 flow 通(mail → notify)。
6. Auth / secret refresh flow 通。
7. 併發 request 行為符合設計(single-flight、rate-limit 等)。
8. External scheduler(cron / CronJob)如預期 fire —— 檢查 silent failure 例如未逃逸的 `%`。
9. Container orchestrator 重啟行為測過(殺一個 pod,看自癒)。
10. Multi-node 部署測過(若聲稱 HA)—— pod 真的落在不同 node,不是只是同 node 多個 pod。
11. Storage class / persistence 測過,pod restart 後 state 有保留。
12. Rollback path 測過 —— 舊版本能讀新版本寫入的 DB state。

v1.0 smoke 期間 fail 掉的所有東西都是「unit test 是必要但不充分」的例子。上面這些課題全部都是 deployment-shape 特定,非得打真 Postgres、真 k3s、真 Google、真 cron 才會冒出來。
