# v1.0 Smoke Test Lessons Learned

> 中文版:[`v1.0-smoke-lessons.zh.md`](v1.0-smoke-lessons.zh.md).
> Companion: [`v1.0-implementation-notes.md`](v1.0-implementation-notes.md)
> catalogs where the shipped v1.0 deviates from the original design.

Consolidated record of everything caught during Proxmox docker + k3s
Helm smoke testing of the `migrate-to-fastapi-service` change
(2026-08-09 to 2026-08-10). Kept in-repo so future migrations of
similar scope have a checklist of "things we know break at deploy
time even when unit tests pass".

## Scope of what got tested

| Environment | What was validated |
|---|---|
| Docker Compose on Proxmox VM | End-to-end mail flow, headless OAuth via SSH tunnel + loopback, in-replica single-flight (10-way concurrent /poll), host cron @ 60s |
| k3s cluster (3 nodes, Longhorn) | Same as above + **cross-node** advisory-lock single-flight (pods on `k3s-node-1` + `k3s-node-3`, k8s Service round-robin, `1×200 + 9×409`), Postgres-backed OAuth FlowStore across replicas, PVC token persistence |

Unit test suite ran clean throughout (559 passing, +1 regression pin added during smoke for the PKCE `code_verifier` bug). Every issue below is one that pytest could NOT have caught without a real deployment target.

## Issues by category

Format: **Symptom → Root cause → Fix (commit) → Prevention added**.

### Environment / packaging

**1. `GmailSettings` reads `GMAIL_*` but deploy templates set `GOOGLE_*`**
- **Symptom**: container crashes at lifespan startup with `FileNotFoundError: OAuth client secrets not found at credentials.json` — the settings fell back to the default `credentials.json` because the env vars we set were never read.
- **Root cause**: `GmailSettings.env_prefix = "GMAIL_"` (v0.6.x convention), but my Dockerfile ENV / .env.example / Helm values.yaml used `GOOGLE_CREDENTIALS_PATH` / `GOOGLE_TOKEN_PATH`. Openspec design D7 also used `GOOGLE_*` — the whole spec-to-code chain had the wrong prefix, but the code side was pinned.
- **Fix**: [`de55a2d`](../commit/de55a2d) — renamed all deploy templates + Dockerfile ENV + Helm values + MIGRATION doc from `GOOGLE_*` to `GMAIL_*`. Openspec artifacts intentionally left with the historical inconsistency.
- **Prevention**: env parity script (`scripts/check_env_parity.py`) covers compose ↔ Helm drift but does NOT cross-check either against the code. A future improvement would parse `BaseSettings` subclasses' `env_prefix + field_name` and verify they appear in the deploy templates. Not implemented — deferred to follow-up.

**2. Host bind-mount ownership mismatch on secrets/data**
- **Symptom**: container startup crashed with `PermissionError: [Errno 13] Permission denied: '/data/token.json'` even though `chmod 600` was set correctly.
- **Root cause**: container runs as uid 10001, but host directories were owned by uid 1000 (default user). Mode 600 = owner-only, so container couldn't read.
- **Fix**: [`755aafe`](../commit/755aafe) — docs (MIGRATION-v1 + deploy/compose/README.md) now explicitly state `sudo chown -R 10001:10001 secrets data`.
- **Prevention**: docs step; no automation. Container could self-heal by running an entrypoint chown before dropping to non-root, but that requires the entrypoint to start as root — trades one small risk (setuid-like startup) for one operational papercut. Chose docs.

**3. Alembic migrations not in image**
- **Symptom**: fresh Postgres DB → first `POST /poll` returned 500 with `sqlalchemy.exc.ProgrammingError: relation "gmail_sync_state" does not exist`.
- **Root cause**: `.dockerignore` excluded `alembic.ini` (and the imaginary `migrations/` directory that doesn't exist in this repo — the actual alembic dir is `alembic/`, which wasn't excluded). Dockerfile didn't COPY either into the runtime image and had no entrypoint that ran `alembic upgrade head`.
- **Fix**: [`10f6327`](../commit/10f6327) — `.dockerignore` no longer excludes alembic; Dockerfile COPYs `alembic.ini` + `alembic/`; new `docker-entrypoint.sh` runs `alembic upgrade head` before uvicorn. Alembic's `alembic_version` row lock makes concurrent multi-replica startups safe.
- **Prevention**: no unit test; the check `entrypoint executes alembic upgrade head` is deploy-shape-specific. A build-time smoke that runs `docker run --rm image alembic current` against a throwaway Postgres would catch regressions.

### OAuth

**4. PKCE code_verifier lost in the flow store round-trip**
- **Symptom**: `/auth/callback` returned 400 with `fetch_token_failed: (invalid_grant) Missing code verifier` after Google's consent screen.
- **Root cause**: `google_auth_oauthlib.flow.Flow.authorization_url()` auto-generates a `code_verifier` for PKCE and stores it on the Flow instance. The `oauth_flows` store serialization dropped it (only kept `scopes` + `redirect_uri`), so the reconstructed Flow at callback time had a fresh verifier that didn't match the challenge Google saw at `/auth/start`.
- **Fix**: [`cfab222`](../commit/cfab222) — `OAuthFlowStore._serialize` now captures `flow.code_verifier`; `_reconstruct` restores it. Regression test in `tests/coordination/test_oauth_flow_store.py::test_roundtrip_preserves_pkce_code_verifier`.
- **Prevention**: the added regression test pins the behavior against future google-auth-oauthlib field renames.

**5. oauthlib rejects scope superset from Google**
- **Symptom**: `/auth/callback` returned 400 with `fetch_token_failed: Scope has changed from "gmail.readonly" to "gmail.readonly drive drive.photos.readonly drive.appdata"`.
- **Root cause**: Google's token endpoint returns every scope previously granted to the user/client pair — often a superset of what the current flow requested (e.g. Drive scopes from an unrelated past consent). oauthlib's default enforcement is strict equality.
- **Fix**: [`7fcb953`](../commit/7fcb953) — set `OAUTHLIB_RELAX_TOKEN_SCOPE=1` in Dockerfile ENV + `os.environ.setdefault(...)` in `core/services.py` (before any oauthlib import path). Documented in `docs/oauth-redirect-uri.md` troubleshooting section.
- **Prevention**: the env var is set unconditionally in both container startup and Python process init — very hard to accidentally regress.

**6. Google OAuth client type shows different UI**
- **Non-issue for us**, but confusing operator experience. `Desktop app` OAuth clients don't show "Authorized redirect URIs" in the Google Cloud Console UI — Google auto-allows `http://localhost:*` and `http://127.0.0.1:*`. Operator following the migration guide's "add redirect URI" step will fail to find the field.
- **Fix**: [`docs/oauth-redirect-uri.md`](oauth-redirect-uri.md) now documents both Desktop vs Web client type differences up front.

### Cron / scheduler

**7. `%` in host crontab is an end-of-command marker**
- **Symptom**: cron log stayed empty despite `syslog` showing CRON firing. Syslog CMD line was truncated: `(david) CMD (curl -fsS -m 55 -w ')`.
- **Root cause**: host cron treats `%` as end-of-command / stdin separator. Unescaped `%{http_code}` in the curl format string truncated the whole command.
- **Fix**: [`9ba2b32`](../commit/9ba2b32) — crontab.example uses `\%{http_code}\n` and documents the gotcha in the header.

**8. Cron does NOT inherit shell env**
- **Symptom**: after fixing `%`, curl returned 401. Manual test with the same shell command worked.
- **Root cause**: `${HTTP_API_KEY}` in the crontab entry was empty at cron execution time — cron doesn't source your shell profile.
- **Fix**: crontab.example instructs to paste the literal key value into the crontab line. crontabs are mode 600 → plaintext is homelab-acceptable.
- **Also**: 24h later I forgot to update the placeholder — got another 401 → obvious in hindsight but a paste-and-run trap. Now called out prominently in the runbook.

### Storage / k8s

**9. `git rev-parse --short` vs `$CI_COMMIT_SHORT_SHA` length mismatch**
- **Symptom**: `ImagePullBackOff` with `manifest not found` — image tag `7f155f5c` didn't exist in registry.
- **Root cause**: `git rev-parse --short` picks the shortest **unambiguous** prefix (usually 7 chars, sometimes longer). GitLab CI's `$CI_COMMIT_SHORT_SHA` is a **fixed 8 chars**. The 8th char I guessed (`c`) was wrong; the real tag was `7f155f51`.
- **Fix**: runbook now says "look at GitLab Container Registry UI for the actual tag" rather than computing locally.
- **Prevention**: for CI-driven deploys, use `$CI_COMMIT_SHORT_SHA` in a helm values override generated inside the pipeline, not computed on operator's laptop.

**10. Helm chart's OAuth token was never mounted**
- **Symptom**: pod crashed at lifespan startup with `webbrowser.Error: could not locate runnable browser` — `get_credentials()` fell through to `InstalledAppFlow.run_local_server()` inside a headless container.
- **Root cause**: `oauth.tokenJson` went into the Kubernetes Secret via `secret.yaml`, but the Deployment's `secret` volume only exposed `credentials.json` as an `items` entry. token.json was in the Secret but not in the pod filesystem.
- **Fix**: [`8c497a1`](../commit/8c497a1) — new `oauth-seed` volume (full Secret contents) mounted only into a new init container `seed-token`, which copies `token.json` to `/data/` on first boot. Guard `[ ! -f /data/token.json ]` prevents overwriting a token written by in-cluster `/reauth`. When `oauth.tokenJson` is empty (fresh deploy), the init container no-ops with a friendly log line.
- **Prevention**: `helm template` renders now covered by `tests/deploy/test_helm_chart.py` but the test asserts kind existence, not volume-mount correctness. A future test could parse the rendered Deployment and assert every expected volume is mounted somewhere.

**11. RWO PVC blocks multi-replica**
- **Symptom**: `helm upgrade --set replicaCount=2` → second pod scheduled to a different node, stuck in ContainerCreating with `Multi-Attach error for volume ... Volume is already used by pod(s) ...`.
- **Root cause**: default `persistence.accessMode: ReadWriteOnce` means the PVC can attach to only one node at a time. First pod on node-3, second pod scheduled to node-1 → attach fails.
- **Fix**: [`77923b7`](../commit/77923b7) — values.yaml documents the RWO ↔ `replicaCount` compatibility issue prominently. Chart default stays RWO (universally supported); users opting into multi-replica must flip to RWX AND have an RWX-capable storage class.
- **Prevention**: docs. Could add a chart-level warning template that renders a comment in the manifest when `replicaCount > 1 && accessMode == "ReadWriteOnce"` but Helm doesn't have first-class validation warnings — would require `.Files.Get` + `fail` which is user-hostile.

**12. Longhorn RWX requires nfs-common on every node**
- **Symptom**: `helm upgrade` with `persistence.accessMode: ReadWriteMany` → `FailedMount: mount failed ... bad option; for several filesystems (e.g. nfs, cifs) you might need a /sbin/mount.<type> helper program`.
- **Root cause**: Longhorn implements RWX via NFS through its share-manager. NFS mount requires `nfs-common` (Debian/Ubuntu) or `nfs-utils` (RHEL/CentOS) on every node that will run the RWX pod.
- **Fix**: no code fix (Longhorn prerequisite, not our chart). Runbook now documents `for node in ...; do ssh $node 'sudo apt install -y nfs-common'; done` as a Phase-A step for Helm.
- **Prevention**: docs. This is a Longhorn-side prerequisite that every RWX-using workload needs.

**13. Port-forward dies when the pod behind it disappears**
- **Symptom**: 10-concurrent test returned 10 × `000` (empty reply) instead of `1×200 + 9×409`. kubectl printed `sandbox not found` errors.
- **Root cause**: `kubectl port-forward svc/...` binds to a specific pod. Any pod restart / helm upgrade replaces the pod, invalidating the forward.
- **Fix**: retry — restart port-forward and re-run. Production uses ingress / LoadBalancer (no such issue).
- **Prevention**: runbook now says "if port-forward errors mid-test, restart it; ingress is the prod path".

### Database

**14. `CREATE DATABASE` without explicit encoding may default to non-UTF-8**
- **Symptom**: analyze + notify ran fine, `_persist` crashed with `psycopg.errors.UntranslatableCharacter: unsupported Unicode escape sequence` writing Chinese keywords.
- **Root cause**: Postgres inherits encoding from `template1`. On some systems `template1` is `SQL_ASCII` — copying Chinese JSON via psycopg's server-side encode fails. v0.6.x users' production DB happened to be UTF-8; the smoke DB was created without `WITH ENCODING 'UTF8'` and inherited SQL_ASCII.
- **Fix**: no code fix — operator-side DB provisioning. Recreated with `CREATE DATABASE ... WITH ENCODING 'UTF8' TEMPLATE template0 LC_COLLATE 'C' LC_CTYPE 'C';`.
- **Prevention**: added to MIGRATION-v1 troubleshooting appendix. A future improvement would have `build_services` run `SHOW server_encoding` at startup and refuse to boot if not UTF8.

## What the smoke actually validated (positive results)

- **D3 advisory lock cross-replica** — proven with 10-way concurrent `POST /poll` on 2 pods across 2 different k3s nodes → exactly 1×200 + 9×409. Not a same-loop asyncio test; a real cross-network, cross-node coordination test.
- **D8 headless OAuth flow** — full round-trip via SSH tunnel + loopback URI (Desktop OAuth client's special case) + PKCE + token reload.
- **D17 multi-replica readiness** — Postgres-backed OAuth FlowStore lets `/auth/callback` land on any replica; verified with 2 pods actively sharing state via the `oauth_flows` table and Longhorn RWX PVC.
- **Alembic auto-provisioning** — fresh DB → entrypoint runs migrations → pod starts uvicorn → `/healthz` green.
- **Init-container token seeding** — deploy with empty PVC + populated Secret → token seeded to `/data/token.json` before main container starts.

## Operator checklist for future migrations of similar scope

Rough order:

1. Unit test suite green.
2. Openspec validate green.
3. `docker build` + `docker run` smoke against a throwaway Postgres.
4. Container starts + `/healthz` returns 200 with all checks true.
5. End-to-end user-facing flow works (mail → notify).
6. Auth / secret refresh flow works.
7. Concurrent-request behavior matches design (single-flight, rate-limit, etc.).
8. External scheduler (cron / CronJob) fires as expected — check for silent failures like unescaped `%`.
9. Container-orchestrator restart behavior tested (kill a pod, check auto-recovery).
10. Multi-node deploy tested (if HA claimed) — pods actually landing on different nodes, not just multiple pods on the same node.
11. Storage class / persistence tested with actual pod restart preserving state.
12. Rollback path tested — old version can read the new version's DB state.

Everything failed at least once during v1.0 smoke was some flavor of "unit tests are necessary but not sufficient". The lessons above are all deployment-shape-specific and would not have surfaced without hitting a real Postgres, real k3s, real Google, real cron.
