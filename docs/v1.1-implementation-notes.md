# v1.1 Implementation notes — deviations from the original design

> 中文版:[`v1.1-implementation-notes.zh.md`](v1.1-implementation-notes.zh.md).
> Companion to [`observability.md`](observability.md). Where that doc
> tells operators how to turn v1.1's observability surfaces on, this doc
> tells future readers of the release how the shipped v1.1 differs from
> what the `add-observability-stack` OpenSpec change said it would be.
> Written after the compose + k3s smoke closed so the frozen design
> artifacts aren't misread as ground truth on details that landed
> differently.

Every deviation below is a bug fix, a mid-flight refactor, or a
smoke-caught operational lesson — not a scope change. Source of truth
for the design intent is the `add-observability-stack` OpenSpec change
(archived at `openspec/changes/archive/2026-08-16-add-observability-stack/`
after this doc lands).

## Rate-limited BSP shape: dedicated submodule, not factory function

Design D24 documents this refactor, but the change went through two
shipped shapes before landing on the final one — worth pinning here so
git blame on the intermediate commits doesn't mislead.

- Group 4a first draft: **wrap-and-delegate** — `RateLimitedBSP` held a
  reference to a real `BatchSpanProcessor` and forwarded each call.
  Silently missed the SDK's newer `_on_ending` protocol method → spans
  ending during shutdown were mishandled.
- Group 4a shipped shape: **factory + class-in-function** — a
  `_make_rate_limited_bsp()` function defined the class inline and
  returned an instance. Fixed the `_on_ending` bug (subclass inherits
  everything) but produced ugly stack traces
  (`_make_rate_limited_bsp.<locals>._RateLimitedBSP`) and blocked
  `isinstance` checks in tests.
- Final shape ([`aa26b02`](../commit/aa26b02), D24): top-level
  `RateLimitedBSP` class in `src/zashiki_warasi/observability/_rate_limited_bsp.py`.
  Lazy import preserved by importing the *module* inside
  `configure_tracing()`'s enabled branch.

## Trace-context factory idempotency: attribute sentinel, not `global`

Design D25 was authored after Group 5 shipped. Group 5 initially used
`global _FACTORY_INSTALLED` at module scope to prevent re-install
stacking. Reviewer flagged `global` as a code smell inconsistent with
the `_HANDLER_SENTINEL = "_zashiki_owned"` pattern already used in the
same file for stream handlers.

- Refactor in [`8371b0c`](../commit/8371b0c) — the wrapper factory
  stamps `__zashiki_installed__ = True` on itself before
  `logging.setLogRecordFactory(wrapper)`; re-install check reads that
  attribute off `logging.getLogRecordFactory()`. Bonus property:
  correctly detects "someone downstream replaced our factory with
  theirs" and re-installs, which module-flag couldn't.
- Regression pin in `tests/observability/test_tracing.py::test_installed_factory_carries_sentinel_attribute`.

## Log format style: f-strings, not `%s` lazy formatting

Group 4a's `zashiki_warasi/observability/tracing.py` shipped with 9
`logger.*` calls using `%s` lazy formatting. Fine in isolation, but
violates the repo convention (memory rule: "inside `logger.*` calls in
this repo, use f-strings, not `%s` lazy formatting; match the existing
convention"). Caught in the Group 4a review pass.

- Fixed in [`d96fd88`](../commit/d96fd88) — all 9 call sites converted
  to f-strings. Behavior identical; consistency restored.

## OTel Collector image pinned to `0.115.1`, not `0.115.0`

`docker-compose.yml` originally pinned `otel/opentelemetry-collector-contrib:0.115.0`.
That tag was never published to Docker Hub (0.115.1 shipped as the
first 0.115.x point release). Caught during compose smoke Phase 9.4
when `docker compose --profile observability up -d` failed with
`manifest for otel/opentelemetry-collector-contrib:0.115.0 not found`.

- Fixed in [`8e9b5db`](../commit/8e9b5db) — bumped to `0.115.1`.
- Prevention: none automated. `docker compose config` doesn't validate
  registry availability of pinned tags; the "CI test job" backlog item
  in `proposal.md` would catch it via a `docker compose pull` step.

## `PROMETHEUS_RETENTION_TIME` + `GRAFANA_ADMIN_PASSWORD` are compose-only

Both env vars appear in `deploy/compose/.env.example` but NOT in
`deploy/helm/zashiki-warasi/values.yaml`. Rationale (see design D20):

- **Prometheus retention** — k3s deploys don't ship a Prometheus; the
  operator's kube-prometheus-stack owns retention via
  `prometheus.prometheusSpec.retention` on the kube-prom-stack chart.
  Our chart has nothing to configure.
- **Grafana admin password** — same reason. K3s Grafana is owned by
  kube-prom-stack.

`scripts/check_env_parity.py` would fail if a key appears in `.env.example`
without a matching values.yaml entry. Both keys were added to the
`COMPOSE_ONLY` allowlist as part of Group 7. Formally covered by
task 8.1; landed early to unblock the test suite during Group 7 authoring.

## Grafana datasource UID must be set explicitly

Not a design deviation, but a compose smoke lesson worth pinning here
because it can't be caught by unit tests and the failure mode ("no
data despite metrics flowing") reads like a Prometheus config problem
rather than a Grafana provisioning problem.

- **Symptom**: compose observability stack up, `curl :9090/api/v1/query`
  returns metrics, but Grafana dashboard panels all say "No data".
- **Root cause**: dashboard JSON hard-codes `"datasource": {"uid": "prometheus"}`.
  Grafana's datasource provisioning YAML didn't set `uid:` explicitly,
  so Grafana auto-generated one (e.g. `PBFA97CFB590B2093`). The
  reference from the dashboard didn't match, so queries silently failed.
- **Fix**: `deploy/compose/observability/grafana/provisioning/datasources.yaml`
  now sets `uid: prometheus` explicitly on both the Prometheus and
  Tempo datasources. Dashboard JSON's `uid:` reference matches.
- **Prevention**: k3s side isn't affected — kube-prom-stack Grafana's
  operator-installed Prometheus datasource carries a well-known uid
  that our dashboard `uid:` doesn't have to match (dashboards imported
  via sidecar can leave datasource selection to Grafana's default).
  Doc callout added to `docs/observability.md` "Troubleshooting" section.

## `helm upgrade --reuse-values` cannot populate new nested defaults

K3s smoke lesson. When upgrading from a chart release that predates the
`observability:` block to one that includes it, `--reuse-values` broke
with `nil pointer evaluating interface {}.key` while rendering
`dashboard-configmap.yaml`.

- **Symptom**: `helm upgrade zashiki ./deploy/helm/zashiki-warasi ... --reuse-values`
  failed template rendering on the `sidecarLabel.key` lookup even though
  the chart's default `values.yaml` clearly defines it.
- **Root cause**: `--reuse-values` uses the OLD chart's values snapshot
  as the base and applies only `--set` leaf keys on top. New nested
  default blocks from the NEW chart's `values.yaml` are NOT merged in.
  So `observability.dashboards.sidecarLabel.key` was `nil` at render
  time even though the file said otherwise.
- **Fix**: use `--reset-then-reuse-values` (helm 3.14+) which uses the
  CURRENT chart's defaults as the base, then applies the OLD release's
  `--set` overrides on top. Correct semantic for "keep my overrides,
  pick up new defaults."
- **Prevention**: doc callout added to `deploy/helm/zashiki-warasi/README.md`
  observability section: any upgrade that crosses a chart version
  introducing new defaults SHOULD use `--reset-then-reuse-values`.

## K3s tracing e2e (task 9.7) skipped — no in-cluster collector

Design D3 assumed operators bring their own OTel Collector when
enabling `OTEL_ENABLED=1` on k3s. Reality on the operator's cluster:
kube-prometheus-stack is installed (Prom + Grafana + Alertmanager),
but no OTel Collector and no Tempo/Jaeger backend. Traces have nowhere
to land.

- Task 9.7 marked skipped in `tasks.md` with note "no collector; deferred
  to follow-up change".
- Design intent unchanged: OTel export is opt-in, endpoint configurable.
  The gap is just infra — app-side code is fully functional (verified in
  compose smoke Phase 9.4 with Tempo).
- Follow-up work item: a future change would ship either chart values
  for `otelCollector.endpoint:` pointing at a shared cluster collector
  (operator installs `otel-collector` chart separately), or bundle
  `opentelemetry-collector` as a chart dependency (heavier — brings
  install/upgrade coordination and adds a decision on receivers).

## Per-alert / per-dashboard toggles verified live

Not a deviation, but worth pinning: design D10 + D19 promised granular
`values.observability.prometheusRule.alerts.<name>.enabled` and
`values.observability.dashboards.<name>.enabled` toggles so operators
can silence individual alerts / dashboards without forking the chart.
Verified live during k3s smoke task 9.6:

- `--set observability.prometheusRule.alerts.tickConflictRateHigh.enabled=false`
  drops the alert from the rendered `PrometheusRule` (verified via
  Prometheus `/api/v1/rules`); re-enabling brings it back.
- `--set observability.dashboards.overview.enabled=false` removes the
  dashboard ConfigMap; the kube-prom-stack Grafana sidecar auto-removes
  the dashboard from Grafana within seconds (verified in sidecar logs:
  `Removing /tmp/dashboards/zashiki-warasi-overview.json`); re-enable →
  sidecar writes it back.

Roundtrip is idempotent — no state carries over between disable/enable
cycles.

## Test count

Original tasks anticipated new test modules under `tests/observability/`
and additions to `tests/core/` (logging), `tests/web/` (routers/middleware),
and `tests/deploy/` (helm chart observability templates). Final layout
matches the plan; no reshuffling.

Final unit test count: **701 passing** (was 559 at v1.0.0). Net addition:
+142 tests across observability (metrics registry, OTel bootstrap, span
tree, GenAI attributes, tracing shutdown), logging (JSON formatter, trace
context factory, whitelist), helm chart (observability template renders
under 5 flag combinations), and web layer (metrics middleware, /metrics
route no-auth semantics).

No test suite splits or skip markers introduced; suite still runs
end-to-end under 2 seconds on a warm cache.
