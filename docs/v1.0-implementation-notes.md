# v1.0 Implementation notes — deviations from the original design

> Companion to [`v1.0-smoke-lessons.md`](v1.0-smoke-lessons.md). Where
> that doc catalogs *what went wrong at deploy time*, this doc catalogs
> *how the shipped v1.0 differs from what the design said it would be*.
> Both were written after the Proxmox docker + k3s Helm smoke closed
> so future readers of the release don't misread the frozen design
> artifacts as ground truth on details that actually landed differently.

Every deviation below is a bug fix or a mid-flight decision, not a
scope change — bigger scope changes would have earned their own
openspec proposal. Source of truth for the design intent is the
`migrate-to-fastapi-service` OpenSpec change (kept locally, archived
at `openspec/changes/archive/2026-08-XX-migrate-to-fastapi-service/`
after PR merge).

## Env var prefix: `GMAIL_*`, not `GOOGLE_*`

Design D7 and the original spec drafts referenced `GOOGLE_CREDENTIALS_PATH`
and `GOOGLE_TOKEN_PATH`. The code side, however, has always used
`GmailSettings.env_prefix = "GMAIL_"` (v0.6.x convention), so the
actual env vars are `GMAIL_CREDENTIALS_PATH` / `GMAIL_TOKEN_PATH`.
The deploy templates initially followed the spec (wrong prefix), got
caught during the first docker smoke run when the container fell back
to the default `credentials.json` and crashed.

- Fixed in [`de55a2d`](../commit/de55a2d) — Dockerfile ENV,
  `.env.example`, docker-compose.yml, Helm values.yaml, MIGRATION-v1.md
  all now use `GMAIL_*`.
- Specs in this change dir (`specs/*.md`) were retroactively corrected
  post-shipping so the sync-to-main-specs won't propagate the wrong
  prefix.
- design.md kept the `GOOGLE_*` phrasing intact as historical record.

## Container entrypoint runs `alembic upgrade head` before uvicorn

Design D5 described the Dockerfile shape but didn't specify a
migrations entrypoint. The v0.5-era Dockerfile did, but I dropped
`alembic.ini` + `alembic/` from `.dockerignore` and forgot to add
either a COPY or an entrypoint hook.

Caught during Proxmox smoke Phase 5.1 — fresh `zashiki_v1_smoke` DB
hit `UndefinedTable` on the first tick.

- Fixed in [`10f6327`](../commit/10f6327) — new `docker-entrypoint.sh`
  runs `alembic upgrade head` against `$DATABASE_URL` then execs CMD.
  Alembic's row-lock on `alembic_version` makes concurrent multi-replica
  boots safe.

## Helm Deployment ships an init container to seed `token.json`

Design D7 said "token.json ... read-write mount that survives container
restarts", but the Helm chart's Deployment volume mounts only included
`credentials.json` from the OAuth Secret. `token.json` went into the
Secret via `oauth.tokenJson` but was never surfaced anywhere the app
could read.

Caught during Helm smoke — first pod crashed with `webbrowser.Error:
could not locate runnable browser` because `get_credentials()` fell
through to `InstalledAppFlow.run_local_server()` inside a headless
container.

- Fixed in [`8c497a1`](../commit/8c497a1) — new `oauth-seed` volume
  exposes the full Secret to a `seed-token` init container that copies
  `token.json` to the PVC on first boot. Guard prevents overwriting a
  token written by in-cluster `/reauth`.

## `OAUTHLIB_RELAX_TOKEN_SCOPE=1` set unconditionally

Design D8 discussed PKCE + the FastAPI-brokered flow but didn't
anticipate that Google's token endpoint returns every scope previously
granted to the user/client pair — often a superset of what the current
flow requested. oauthlib's strict scope-equality check rejects the
exchange.

Caught during Proxmox smoke Phase 5.2. The affected client had Drive
scopes previously granted, which came back attached to the reauth's
token → `fetch_token_failed: Scope has changed`.

- Fixed in [`7fcb953`](../commit/7fcb953) — `OAUTHLIB_RELAX_TOKEN_SCOPE=1`
  set in Dockerfile ENV AND `os.environ.setdefault(...)` in
  `core/services.py` before any oauthlib import path fires. Applies
  to both container and CLI runtimes.

## PKCE `code_verifier` persisted in the OAuth flow store

Design D8 described the OAuth flow store as holding "`client_config`,
`_scopes`, `_redirect_uri`, `_state`, OAuth session token if any" —
missed `code_verifier`. google-auth-oauthlib's
`Flow.authorization_url()` auto-generates the PKCE verifier and stores
it on the flow instance; the reconstructed Flow at callback time had
a fresh verifier that didn't match the challenge Google saw.

Caught during Proxmox smoke Phase 5.2: `fetch_token_failed:
(invalid_grant) Missing code verifier`.

- Fixed in [`cfab222`](../commit/cfab222) — `OAuthFlowStore._serialize`
  captures `flow.code_verifier`; `_reconstruct` restores it. Regression
  test in `tests/coordination/test_oauth_flow_store.py::test_roundtrip_preserves_pkce_code_verifier`.
- The relevant sentence in `specs/headless-authentication/spec.md`
  ("Flow serialization: ... SHALL be extracted to JSON") was left
  intact — `code_verifier` is one of the fields that "reconstructable
  state" now includes; the code + regression test are the source of
  truth.

## Helm chart supports `imagePullSecrets` for private registries

Not covered in the original design or specs — the initial chart
assumed a public image (Docker Hub / public GHCR). Added mid-smoke
when deploying to the self-hosted GitLab registry at
`gitlab.davidho.dev:5050`.

- Added in [`d7ddfec`](../commit/d7ddfec) — `imagePullSecrets` value
  is an empty list by default (no-op), populated by operators pulling
  from private registries. Both Deployment and CronJob honour it.

## RWO ↔ replicaCount compatibility contract

Design D17 stated `replicaCount > 1` was safe, but the Helm chart
defaulted `persistence.accessMode: ReadWriteOnce` — which blocks
multi-node scale-up (`MultiAttach error`). Compatibility contract
was implicit; now documented explicitly in `values.yaml`.

- Documented in [`77923b7`](../commit/77923b7). No code change; the
  default stays RWO (universally supported); operators opting into
  multi-replica must flip to RWX + have an RWX-capable storage class.

## Longhorn RWX prerequisite: nfs-common on every node

Not our chart's issue — but caught during Helm smoke Phase E and
important enough for the operator docs. Longhorn RWX implements share
via NFS via its share-manager; every node running an RWX pod needs
`nfs-common` (Debian/Ubuntu) or `nfs-utils` (RHEL/CentOS).

Documented in `docs/v1.0-smoke-lessons.md` issue #12.

## Host cron gotchas (`%` escaping + shell env)

Design didn't mention them because "external cron drives cadence" was
described at a higher level. Ran into two of them during Proxmox
smoke Phase 6: unescaped `%{http_code}` silently truncated the cron
line; `${HTTP_API_KEY}` in the crontab entry was empty at execution
time because cron doesn't source the shell profile.

- Fixed in [`9ba2b32`](../commit/9ba2b32) — `crontab.example` now
  escapes `%` and instructs paste-the-literal-key, with the gotchas
  called out in the file header.

## Postgres UTF-8 encoding is a hard requirement

`_persist` writes Chinese JSON to `email_analyses.keywords`. A
`SQL_ASCII`-encoded database (default from `template1` on some
systems) crashes with `psycopg.errors.UntranslatableCharacter`. This
was never a design issue — v0.6.x prod DB happens to be UTF-8 — but
smoke's fresh test DB was created without explicit encoding.

- No code fix (operator-side DB provisioning). Documented in
  MIGRATION-v1.md troubleshooting appendix + README Requirements.
- Future improvement (not shipped): `build_services` could
  `SHOW server_encoding` at startup and refuse to boot if not UTF8.

## Test count

Original tasks anticipated new test modules under `tests/web/`,
`tests/coordination/`, and `tests/auth/` (task 17.1). The actual
layout is `tests/web/` + `tests/coordination/` + `tests/deploy/`
(env parity + Helm chart lint) — no separate `tests/auth/`; auth
tests live in `tests/web/test_auth.py`.

Final unit test count: 559 passing (was 476 at v0.6.0). One
regression pin added during smoke (PKCE); the other +82 came from
the 6 authoring sessions.
