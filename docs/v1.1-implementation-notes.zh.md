以下每條都是 bug fix、midway refactor,或 smoke 抓到的 operational lesson
—— 都不是 scope change。設計意圖的 source of truth 是
`add-observability-stack` OpenSpec change(這份文件落地後 archive 到
`openspec/changes/archive/2026-08-16-add-observability-stack/`)。

## Rate-limited BSP 的形狀:專用 submodule,不是 factory function

設計 D24 有記錄這次 refactor,但實際 shipped 過兩個中間形狀才落到最終形,
在這裡 pin 一下避免 git blame 上中間 commit 誤導。

- Group 4a 初稿:**wrap-and-delegate** —— `RateLimitedBSP` 內部持有一個
  真的 `BatchSpanProcessor`,每個呼叫轉發過去。悄悄漏掉 SDK 新版的
  `_on_ending` protocol method → shutdown 期間收尾的 span 被處理錯。
- Group 4a shipped 形狀:**factory + class-in-function** ——
  `_make_rate_limited_bsp()` function 內部定義 class 再回傳 instance。
  修好了 `_on_ending`(subclass 天生繼承),但 stack trace 變醜
  (`_make_rate_limited_bsp.<locals>._RateLimitedBSP`),測試裡也沒辦法
  做 `isinstance` check。
- 最終形([`aa26b02`](../commit/aa26b02), D24):top-level 的
  `RateLimitedBSP` class 放在
  `src/zashiki_warasi/observability/_rate_limited_bsp.py`。Lazy import
  由 `configure_tracing()` 的 enabled 分支裡「import 那個 module」達成。

## Trace-context factory 冪等性:attribute sentinel,不用 `global`

設計 D25 是 Group 5 shipped 之後才寫進去的。Group 5 一開始在 module
scope 用 `global _FACTORY_INSTALLED` 來防止重複安裝疊 wrapper。Review 時
指出 `global` 是 code smell,且和同檔案裡 stream handler 已經在用的
`_HANDLER_SENTINEL = "_zashiki_owned"` pattern 不一致。

- Refactor 在 [`8371b0c`](../commit/8371b0c) —— wrapper factory 在自己
  身上蓋 `__zashiki_installed__ = True` 之後才呼叫
  `logging.setLogRecordFactory(wrapper)`;重裝檢查從
  `logging.getLogRecordFactory()` 拿 attribute 讀。額外好處:如果下游有
  人把 factory 換成別的,attribute check 可以正確判斷「不是我們的」而
  重新安裝 —— module flag 分辨不出。
- Regression pin 在
  `tests/observability/test_tracing.py::test_installed_factory_carries_sentinel_attribute`。

## Log format 風格:f-string,不用 `%s` lazy formatting

Group 4a 的 `zashiki_warasi/observability/tracing.py` shipped 時裡面有
9 個 `logger.*` 呼叫用 `%s` lazy formatting。單看沒問題,但違反 repo 慣
例(memory rule:「inside `logger.*` calls in this repo, use f-strings,
not `%s` lazy formatting; match the existing convention」)。Group 4a
review 抓到。

- 修在 [`d96fd88`](../commit/d96fd88) —— 9 個呼叫點全轉 f-string。行為
  一樣,一致性回來。

## OTel Collector image pin 到 `0.115.1`,不是 `0.115.0`

`docker-compose.yml` 原本 pin `otel/opentelemetry-collector-contrib:0.115.0`。
那個 tag 從沒 push 上 Docker Hub(0.115.1 才是 0.115.x 系列的第一個
point release)。Compose smoke Phase 9.4 執行
`docker compose --profile observability up -d` 時炸,錯誤是
`manifest for otel/opentelemetry-collector-contrib:0.115.0 not found`。

- 修在 [`8e9b5db`](../commit/8e9b5db) —— bump 到 `0.115.1`。
- Prevention:無自動化。`docker compose config` 不會去 registry 驗 tag
  是否存在;`proposal.md` backlog 提到的 CI test job 若有跑
  `docker compose pull` 就能抓到。

## `PROMETHEUS_RETENTION_TIME` + `GRAFANA_ADMIN_PASSWORD` 是 compose-only

兩個 env var 出現在 `deploy/compose/.env.example`,但**不會**出現在
`deploy/helm/zashiki-warasi/values.yaml`。理由(見設計 D20):

- **Prometheus retention** —— k3s 部署本身不 ship Prometheus,operator
  的 kube-prometheus-stack 才擁有 retention(在 kube-prom-stack chart
  的 `prometheus.prometheusSpec.retention`)。我們 chart 沒東西可調。
- **Grafana admin password** —— 同理。K3s 的 Grafana 是 kube-prom-stack
  管的。

`scripts/check_env_parity.py` 只要一邊有一邊沒就會 fail。這兩把 key 是
Group 7 期間加進 `COMPOSE_ONLY` allowlist 的。正式歸屬 task 8.1,但 Group 7
執行時就提前落實以解 test 卡點。

## Grafana datasource UID 必須顯式設

不是設計 deviation,是 compose smoke 學到的一課,但值得 pin —— 這個問題
單元測試抓不到,且 failure mode(「metrics 有進來但 dashboard 一片 No data」)
讀起來像 Prometheus 設定問題,實際是 Grafana provisioning 問題。

- **症狀**:compose observability stack 起來,`curl :9090/api/v1/query`
  拿得到 metrics,但 Grafana 面板全顯示 "No data"。
- **Root cause**:Dashboard JSON 硬碼
  `"datasource": {"uid": "prometheus"}`。Grafana 的 datasource
  provisioning YAML 沒顯式設 `uid:`,於是 Grafana 自動 gen 了一個
  (例如 `PBFA97CFB590B2093`)。Dashboard 引用對不上,query 靜默失敗。
- **修法**:`deploy/compose/observability/grafana/provisioning/datasources.yaml`
  在 Prometheus + Tempo 兩個 datasource 上顯式加 `uid: prometheus`(和
  `uid: tempo`)。Dashboard JSON 的 `uid:` reference 對上了。
- **Prevention**:k3s 側不受影響 —— kube-prom-stack 的 Grafana 有自己
  Operator 裝好的 Prometheus datasource,uid 是眾所皆知的,我們透過
  sidecar 匯入的 dashboard 讓 Grafana 自己選 datasource 就好。已在
  `docs/observability.md` "Troubleshooting" 加註。

## `helm upgrade --reuse-values` 帶不進 chart 新增的 nested default

K3s smoke 學到的一課。從一個沒有 `observability:` block 的 chart 版本
升上有 `observability:` 的版本時,`--reuse-values` 在 render
`dashboard-configmap.yaml` 時炸 `nil pointer evaluating interface {}.key`。

- **症狀**:`helm upgrade zashiki ./deploy/helm/zashiki-warasi ... --reuse-values`
  在 render `sidecarLabel.key` 時報 nil pointer,即使 chart 的 default
  `values.yaml` 明明有寫。
- **Root cause**:`--reuse-values` 用**舊 chart 的 values snapshot**當
  base,只在上面套 `--set` 的 leaf key。新 chart `values.yaml` 帶進來的
  nested default block **不會**合併進來。所以
  `observability.dashboards.sidecarLabel.key` render 時是 `nil`,即使
  文件裡有預設值。
- **修法**:改用 `--reset-then-reuse-values`(helm 3.14+),它用**當前
  chart 的 defaults** 當 base,再把舊 release 的 `--set` 覆寫套上去。
  「保留我的 override,但吃到新的 defaults」正確的語意。
- **Prevention**:已在 `deploy/helm/zashiki-warasi/README.md` observability
  section 加註 —— 任何跨 chart 版本、新版帶進 default 的 upgrade,都應
  該用 `--reset-then-reuse-values`。

## K3s tracing e2e (task 9.7) 被 skip —— 集群無 collector

設計 D3 假設 operator 開 `OTEL_ENABLED=1` 時自備 OTel Collector。實際情
況:operator 的 cluster 有 kube-prometheus-stack(Prom + Grafana +
Alertmanager),但沒 OTel Collector,也沒有 Tempo/Jaeger 之類的 trace
backend。Span push 出去沒人收。

- Task 9.7 在 `tasks.md` 標 skip,備註「no collector; deferred to
  follow-up change」。
- 設計意圖不變:OTel export 是 opt-in,endpoint 可設。缺的只是 infra
  —— app-side 程式 100% 就緒(已在 compose smoke Phase 9.4 用 Tempo 驗過)。
- Follow-up:未來的 change 會做 chart values 讓 `otelCollector.endpoint:`
  指到一個共享 cluster collector(operator 另外裝 `otel-collector`
  chart),或者把 `opentelemetry-collector` 塞成 chart dependency(更重
  —— 帶進安裝/升級協調,還得決定 receiver 陣容)。

## Per-alert / per-dashboard toggle 已 live 驗過

不是 deviation,值得 pin:設計 D10 + D19 保證了
`values.observability.prometheusRule.alerts.<name>.enabled` 和
`values.observability.dashboards.<name>.enabled` 這種粒度到單一項目的
開關,讓 operator 可以單獨關掉某條 alert / 某張 dashboard,不用 fork
chart。K3s smoke task 9.6 現場驗:

- `--set observability.prometheusRule.alerts.tickConflictRateHigh.enabled=false`
  能把該 alert 從 rendered `PrometheusRule` 拿掉(Prometheus
  `/api/v1/rules` 驗過);開回去它會回來。
- `--set observability.dashboards.overview.enabled=false` 移掉
  dashboard ConfigMap;kube-prom-stack Grafana sidecar 幾秒內就從
  Grafana 自動移除(sidecar log 有
  `Removing /tmp/dashboards/zashiki-warasi-overview.json`);開回來 →
  sidecar 又 write 回去。

Roundtrip 是冪等的 —— disable/enable 循環之間沒有殘留 state。

## Test 數

原始 tasks 預期 `tests/observability/` 新 test module + `tests/core/`
(logging)、`tests/web/`(routers/middleware)、`tests/deploy/`(helm
chart observability template)的加碼。最終佈局跟計畫吻合,沒有重排。

最終 unit test 數:**701 passing**(v1.0.0 是 559)。淨增:+142 個
test,分佈在 observability(metrics registry、OTel bootstrap、span tree、
GenAI attribute、tracing shutdown)、logging(JSON formatter、trace
context factory、whitelist)、helm chart(observability template 在 5
組 flag 組合下 render)、web layer(metrics middleware、/metrics 無驗
證語意)。

沒有分裂 test suite 或加 skip marker;整套仍能在 warm cache 下 2 秒內跑
完。
